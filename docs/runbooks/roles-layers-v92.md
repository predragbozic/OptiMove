## What it changes

- Eight new tables (club ceiling, club versions of system roles, custom roles of one user; each with items and an
  append-only change record), all empty after the migration; row-level security on, no grant to PUBLIC / `anon` /
  `authenticated` / `service_role`.
- The twin of `can()` (`public.user_has_permission`) with the layers (ceiling, then custom -> club version -> role), its
  companions `user_holds_role_items` and `lock_permission_actor` (which now **requires** the club's ceiling lock for a club
  or team scope: `55000` otherwise), v84's rule 7 also over every club with a live version, and the request record
  widened for R4-3's operations.
- Two triggers on each of `public.user_club_roles` and `public.user_team_roles`: a change of `is_active` or `revoked_at`
  always moves `updated_at`; a change of `updated_at` ends the live custom roles made on that row. With no custom role in
  the database (the state after the deploy) the second does nothing.
- The seed: the eleven VIEW words of contract 4.1 into Club admin and Team coach. **Nobody gains or loses anything**: no
  route checks a view word yet (`ENFORCED_PERMISSIONS` in `backend/src/permissions.js`), and `/me` offers only checked
  words. Proof: `roles-r4-v92.test.mjs` test 3 (old-vs-new of the twin: only the seeded view words differ, only for their
  holders), `roles-r4-view-seed-proof.test.mjs` (every seeded holder reaches the module's read gate today).

## Order against v93

Production applied v93 (`202611251000`, calendar) before v92; a fresh database applies v92 first by name. v92 names no
calendar object and v93 none of v92's. Both orders give the same v92 objects: `roles-r4-v92.test.mjs` test 1, and the
rehearsal below builds production's order.

## Deploy

The server code of R4-1 and v92 go together: the new `ROLE_PERMISSIONS_SQL` reads `public.permission_user_holdings`, and
the Roles API takes the club lock that `lock_permission_actor` now checks. During the start of the new server the
migrator applies v92 first (`npm start`), so the new code never runs without it. The old server running against v92 for
the seconds of a deploy: its role writes call `lock_permission_actor` without the club lock and answer `500` (nothing
written); its reads answer as before. Deploy at a quiet moment.

**M5 (contract 7.7):** once a ceiling row, a club version or a custom role exists, the server may not go back below R4-1
(an older `can()` would answer by the default roles alone). The rollback refuses then anyway.

## Preflight and post-check on production

Read-only, each block in `begin transaction read only; ... rollback;`. Every column ending in `ok` must be true.
Post-check block 1 prints the recorded checksum: compare it with the file's sha256.

## Rollback

`psql -v ON_ERROR_STOP=1 -f roles-layers-v92-rollback.sql`, one transaction, at a quiet moment, on its own approval, and
only after the deployed commit no longer contains v92 and runs the server code from before R4-1. It refuses (23514,
nothing changed) once any layer was used, any migration was applied after v92, a v92 body changed, or the basic roles
changed after the seed. It restores v84's six bodies (checked by md5 before the commit), drops v92's objects, puts the
request record back to v84's shape and removes the seeded words through v84's guarded path (the change rows stay as
history).
