# Exercise blocks: catalog and discovery

## Reused architecture

Application blocks remain `library.exercise_collections`, existing system-exercise membership and explicit user grants. An exercise still belongs to at most one application block. Private copies remain owned, retain provenance, and require access to the canonical source. Collections are not program templates and no exercise or program copies are created by browsing, selecting or assigning a block.

Administration still requires a real platform-admin role in the selected platform workspace. Everyone else receives only authorized content, or deliberately configured discovery previews. Existing collection revisions, audit records, shared reuse/exclusive grant mutation guards, access-change realtime invalidation and UNIQUE indexes are retained.

## Added behavior

- Blocks button in Exercise Library (beside the view switcher) opens template-style package cards. All exercises returns the ordinary library; opening an available block uses the same list, search, filters and existing view modes with a server-side block predicate, and the open block shows as a chip "Block: <name>" whose x returns to all exercises. Block administration is only in the Blocks view: a gear (Manage application blocks) and Edit block on each card; never in the library list, also not inside a block (owner, 2026-10-17).
- Other is a virtual group of accessible exercises whose canonical original belongs to no application block. It never grants access to unassigned restricted exercises and is not stored as a collection. Existing private source copies are grouped by their canonical original.
- Card cover uses an explicit HTTP(S) image URL, otherwise the first visible active original in alphabetical name/ID order. Missing first-image data produces a placeholder. A locked block never falls back to restricted exercise media; only the administrator's explicitly supplied presentation cover may be shown.
- Editor adds description, cover URL and staged checkbox selection with Add selected. Pending choices survive searches; selections only persist after Save. Conflicting membership is still rejected transactionally. Exercise removal from a block is not exercise deletion. No new order editor was introduced; the existing alphabetical membership order is retained.
- Assign uses existing selected-user grants, or explicit all-users access (including future authorized application users). Existing selections are retained while everyone is enabled. Legacy PATCH clients that omit new fields preserve their current values.
- Administrator configures block discovery and exercise discovery separately: hidden, or locked. Both default to hidden, including on existing blocks. Locked block cards expose presentation metadata/counts; locked exercise previews expose only ID/name and an explicitly visible block name (null for a hidden block), never instruction/video/image URLs, editable detail or reusable exercise objects. They cannot be copied, tagged, played or inserted through those previews. Real read/reuse/copy ACL still denies direct requests.
- The Exercise Library's search asks for a separate locked-preview list in the same response (`lockedPreviews=1`, computed only for the first page, `offset=0`; the library pages by a growing limit); no additional frontend search request or breaking cache/parallel-start behavior. The Builder's offset-paged search does not ask and gets none. Previews are name matches, shown for active/unhidden system browsing without personal/classification/owner filters, not Favorites/Marked/private/archive result substitutes.
- A block save or a realtime access change reads the coach's current screen again (`reloadExerciseLibrarySurface`): the Blocks view stays the Blocks view.
- A cover URL must start with `http://` or `https://` (the database CHECK) and may carry no user name or password; covers load with `referrerpolicy="no-referrer"`. The catalog does not return `accessAll` to coaches.
- Rename and delete (owner, 2026-10-17). A block is renamed in its editor (Block name, then Save; the editor says so for an existing block). Delete block in the editor (`DELETE /api/exercise-collections/:id` `{ expectedRevision }`, the revision the editor loaded) removes the block's exercises from it — they are back in Other, available to every coach; the exercises themselves and personal copies are untouched — and its user grants, in one transaction with the same lock, platform-admin check and audit row as a save (`after_state` `{ id, name, deleted: true, exerciseCount, userCount }`; the transaction is READ COMMITTED with a 15 s idle bound, because it holds the exclusive block lock every exercise reuse takes shared). Once the COMMIT is sent the answer never says "not deleted": a COMMIT error is checked on another connection — found, `200` with `verifiedAfterCommitError: true`; otherwise `503 outcomeUnknown`; the editor shows both unknown cases, and a lost answer after its 45 s client bound, as "Delete was not confirmed". The row stays, marked `deleted_at` / `deleted_by_user_id`, because the audit references it; a deleted block is gone from the catalog, the admin list and every edit (the same 404 as a missing one), and a repeated delete is that 404. The editor's confirmation names the block, how many exercises move to Other and that it cannot be restored.
- The block editor's exercise and user pickers filter while typing (250 ms after the last keystroke, Enter at once; no Search button; a slower older answer never replaces a newer one, and the caret stays where it was).
- One exercise's block from the exercise itself (owner, 2026-10-17): the administrator's My classification panel has an "Application block" section above the personal fields — a choice of every live block or Other, with its own "Move to this block" button and a confirmation that names who can use the exercise afterwards (a restricted block's users and the administrator, losing it for other coaches including their personal copies; everyone for an open block or Other). It is never part of the personal Save. `GET /api/exercise-collections/exercise-block/:exerciseId` gives the exercise's current block (a private copy's is its original's, shown read-only, `movable: false`) and the live blocks; `PUT` the same path `{ collectionId | null, expectedCollectionId | null }` moves it: administrator only (the router's 404 otherwise), only an active system exercise (`400 invalidSelection`), only to a live block (`409 blockNotAvailable`), only from where the screen showed it (`409 staleRevision`; a repeat of a move already made answers `changed: false` and writes nothing). Both blocks get a new revision — an editor open on either sees it changed — and an audit row each, in one transaction with a block save's lock order (block lock, administrator, the blocks by id, the exercise); the COMMIT outcome is classified like a delete's (`verifiedAfterCommitError` or `503 outcomeUnknown`). The panel bounds the move at 45 s and stays open while it runs.
- Access-required text directs the user to the administrator. This change does not send access-request notifications, implement payments, publish a marketplace, import a paid package or grant access automatically.

## Migration and release

`202610162230_exercise_block_catalog.sql` only adds five metadata columns to existing collections: description, cover_image_url, access_all, block_preview, exercise_preview. Defaults preserve existing restrictions; there are no new tables, changed memberships, deleted records, FK/UNIQUE changes or program/media rewrites. Migration uses the repository's existing migrations_v2 runner and must run before the new backend starts. Normal brief ALTER TABLE locks remain a deployment consideration; the official local migration runner is covered by a populated preservation test. No database rollback should be automatic.

`202610171200_exercise_block_soft_delete.sql` adds `deleted_at` and `deleted_by_user_id` (both or neither) and three triggers that hold for every writer: an exercise or a user grant never joins a deleted block, a block is marked deleted only once it holds neither and only under READ COMMITTED (an older REPEATABLE READ snapshot could miss a member), and a deleted block is never changed again — any later `UPDATE` of the table filters `deleted_at is null` (`23514`). The membership trigger takes the block row `FOR SHARE`, so an insert racing a deletion is refused in either order (tested with two connections). The database does not require the audit row or that the deleting user is an administrator (the route does both); that, and an owner role able to disable triggers, is the same limit as the rest of the library. The two access readers that join the block table (`access_all` in `exerciseCollectionAccessSql`, the locked previews) also filter `deleted_at is null`, so access never depends on the "deleted means empty" rule alone. Rollback: `docs/runbooks/exercise-block-soft-delete-rollback.sql` (`psql -v ON_ERROR_STOP=1 -f`, its own transaction, the three tables locked before the checks), refused once any block was deleted, when the migration is not recorded, or when a later migration is recorded; rollbacks run newest first. An older application left on this schema would list a deleted block as an empty live one.

Pictures: Big (library and Builder) and Details show the whole picture over a blurred copy of it; Tile and List crop to the frame aimed at the upper body. YouTube keeps its 320 px 16:9 cover even there: its larger covers are 4:3 with black bars around the video (above and below a 16:9 one, beside a vertical one), which no frame can crop away without knowing the video's shape. Drive covers are 1000 px in Big and Details.

An older application ignores discovery metadata and all-users access; application rollback would hide newly public content from users lacking individual grants, rather than grant additional access. Leave additive columns in place. No production schema or data writes, merge, deployment, backup or restore are authorized by this implementation.

## Known limits (post-merge review, 2026-10-17)

Recorded, not fixed:
- A block card's count is the package size (active system originals); the opened list also shows the coach's own private copies of them.
- `/catalog` runs its statements one after another and recomputes Other on every search keystroke.
- A copy of a private copy has no `source_exercise_id` (database CHECK), so it is grouped under Other, not under its root's block.
- The administrator flag is derived per statement (no single workspace snapshot per request); every statement still applies the ACL on its own.
- A locked block's count is shown even when its exercise previews are hidden.
- Creating a block (POST) is not idempotent: a repeated submit can make a second block.
