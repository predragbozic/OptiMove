# Training Load — Analysis Dashboard UX contract (design only, no frontend code)

**Round 4 (final blocker-correction pass).** Updated to match the corrected model (`DASHBOARD_MODEL_REPORT.md`, §0-R4): the Group-by control gains a real **Week** option and correct **Session/Component** semantics (one row per real session/component, never a shared date bucket), and "Team" is renamed **Squad (selection)** to match the model's own honestly-named `group_by='cohort'`; a genuine **measurement conflict** state is added (distinct from a unit conflict) for the case where a widget's own bucket depends on an unresolved same-target conflict; the comparison-period caption now states its real Monday-Sunday/leap-day policy when relevant. Round 3's own additions (real aggregation picker, corrected source-policy control, generalized workspace label) and Round 2's (data-workspace label, atomic layout-save, unit-conflict/ambiguous-template/stale-revision/revoked-workspace states) carry forward unchanged except where called out below.

Textual UX contract for desktop, tablet, and mobile. Style: neutral white/gray surfaces, SVG line icons matching Tests/Calendar, teal (`var(--accent)`) reserved for active selection, warning, conflict, or status — never a large solid color block, exactly as the rest of Training Load already does. No visual mockup tool was used; this is the same textual-contract format the Calendar phase's own UX decisions were driven by.

---

## Desktop (and any viewport ≥ ~960px)

### Layout
- A **12-column grid**, same visual density as the rest of the app's card-based sections — no dedicated "dashboard chrome" that looks foreign to Training Load.
- Two modes: **View** (default) and **Edit**, toggled by a single header button ("Edit layout" / "Done editing" — never a padlock icon or a modal; the grid itself gains a light dashed outline and per-widget drag handles only while in Edit mode).

### Header row
```
[Dashboard name ▾]   [Data: Club A ▾]*   [Global filter: period · activity · athletes ▾]   [Edit layout]   [⋮]
```
`* only shown for a PRIVATE ('user'-owned) dashboard — see below.`
- **Dashboard name ▾** — click opens the dashboard switcher (recently used + "Browse all" + "New dashboard"). If the current dashboard is a template being viewed (not yet cloned) by someone who cannot edit it, this shows a small neutral "Template" tag next to the name and offers **Clone** instead of **Edit layout**.
- **Data: Club A ▾ (Round 2, new; label text generalized in Round 3)** — a small, neutral, non-editable label naming the dashboard's own fixed data workspace (model report §0.1/§0-R3.2) — shown ONLY for a private dashboard, since a club/team dashboard's data workspace is always obviously "this club/team" and a system template shows nothing here (it has none until cloned). This label is never a dropdown/picker in this phase — a private dashboard's data workspace is write-once at creation (model report §0.1); changing it means creating a new dashboard, not editing this one. The label text depends on the dashboard's real `data_workspace_type` (all 5 values, §0-R3.2), not just club: **club** → *"Data: Club A"*; **team** → *"Data: Team A1"*; **private_coach** → *"Data: My own sessions"*; **athlete** → *"Data: My own training"* (bound at query time to whoever is currently viewing, never a fixed name); **platform** → *"Data: All clubs (platform-wide)"*, with a slightly stronger visual treatment (still neutral, never a warning color) since this is the one workspace with no scope narrowing at all. Hovering any of them explains the SAME thing in plain language, e.g. for platform: *"This dashboard always shows data across every club, even when you switch to a specific one."*
- **Global filter** — a single compact control combining period, the Calendar-provided `activityId`/`componentId` context (when arriving from Calendar, pre-filled and visually pinned with a small "from Calendar" hint), and athlete/team selection. Opens the same recipient-style picker pattern already used elsewhere in Training Load (Club/Team/Athletes tabs) — not a new picker design. **The Calendar activity context is ALWAYS a runtime filter only** (model report §0.1/§4) — arriving from an activity pre-fills this control, and nothing else; it is never written to `dashboards.default_filter` unless the coach takes the separate, explicit **Save as default** action below. Switching activities, dates, or athletes while browsing never silently overwrites the dashboard's own saved default.
- **⋮** — Rename, Duplicate, Archive (with the same "this has X active viewers/clones" confirmation copy pattern Training Load already uses for destructive-feeling actions), **Save as default** (the ONLY action that ever writes the current runtime filter into `dashboards.default_filter` — a plain filter change by itself never does this).

### View mode
- Widgets render read-only. Clicking a KPI/chart/table row that maps to a specific athlete/activity/component narrows the *global* filter (never silently mutates a widget's own saved config) — same "runtime filter, not a saved rewrite" rule as above.
- A widget that failed its own query (batch partial-error, model report §0.9) shows a small inline error state **scoped to that one widget** — never a full-page error, never blocking the other widgets.
- A widget whose series resolved to nothing (e.g., a template's hint never matched anything in this workspace) shows a neutral "No matching metric available" empty state, not a red error.
- **Unit conflict (Round 2, new)** — when a widget's own query result comes back with `unitConflict: true` (model report §0.7: the same series has historical values in more than one real-world unit, e.g. meters then kilometers), the widget shows a neutral inline notice — *"This metric's unit changed partway through the selected period (m → km) — shown separately below"* — and renders the values as two clearly labelled sub-groups (never blended into one number, never silently converted, never picking one unit and mislabeling the other).
- **Measurement conflict (Round 4, new — a DIFFERENT state from unit conflict)** — a bucket (a day, a week, a session — whatever the widget's own `group_by` shows) can come back with `conflict: true, value: null` when two or more real readings exist for the exact SAME underlying measurement (same athlete, same real session/day, same metric, same unit) and no single source policy was pinned to resolve it. That one bucket shows a neutral inline marker (a small "⚠" dash instead of a number) with a tooltip: *"Two different readings exist for this — pick a source to see a value here."* Tapping/clicking it opens the same source-policy picker already in the widget's own series options, pre-scoped to just the real candidate values shown with their own provenance (entry method / connection / manual). The REST of the widget's other buckets render completely normally — one conflicted bucket never blanks the whole chart/table. A **type/semantic conflict** (a historical metric definition change — its value type or its own daily-reduction method changed between two versions landing in the same bucket) renders the same neutral marker with a different tooltip: *"This metric's definition changed and can't be safely combined here — showing by version instead."* and the widget falls back to one row per real historical version rather than guessing.
- **Access revoked (Round 2, new)** — if a request for this dashboard's own data comes back unauthorized (the coach's role in its bound data workspace was revoked since the dashboard was last opened — model report §0.1/§1.6), the WHOLE dashboard (not just one widget) shows a neutral full-panel notice — *"You no longer have access to Club A — this dashboard's data can't be shown."* — with no query attempted for any widget. The dashboard's own saved configuration is never touched by this state; regaining the role makes the dashboard work again with no re-save needed.

### Edit mode
- **Add widget** — a button opens a small picker: widget type (4 icons — KPI/Table/Line/Bar) → metric/series picker (same domain/category/search UI as the Calendar's own metric picker, reused verbatim, not redesigned; only definitions actually visible to this dashboard's own data workspace are offered — model report §0.1) → **series options**:
  - **How to combine multiple readings (Round 3, reworked; wording corrected in Round 4)** — a real, freely-choosable control: *Sum / Average / Maximum / Latest / Show every reading*, never locked. **The pre-fill differs by series kind, precisely** (Round 2/3's text here wrongly implied every metric carries this hint — only built-ins do): for a **built-in series** (RPE/sRPE/Duration/session count/last session), pre-filled from that built-in's own real `dashboard_builtin_series.default_analytical_aggregation` pick-list hint; for a **real Metrics-Core metric**, there is no such stored UI-default field at all — the picker simply starts at `Sum` (the column's own DB default) and, as a soft, clearly-labelled suggestion only, may show the metric's OWN `daily_aggregation_method` next to the control (*"this metric's own daily total is normally summed"*) without pre-selecting it. The SAME metric can back a "weekly total" widget elsewhere and a "per-session average" widget here, and both are legal. A short inline note the first time a coach opens this control: *"This is how THIS widget summarizes the readings — it doesn't change how the metric itself is recorded."*
  - **Group by (shown next to the combine-control above; Round 4 wording correction)** — *Day / Week / Session / Component / Athlete / Squad (selection)* — governs what one row/point/bar represents. **"Squad (selection)"**, never "Team" (Round 2/3's own draft copy) — matching the model's real `group_by='cohort'` value: it merges whichever athletes are CURRENTLY selected in the active filter into one combined number, not a real club/team roster; a true "one row per real roster team" view does not exist yet — see model report §0-R4.1. **"Week"** is new this round — a real Monday-Sunday bucket. **"Session"/"Component"** now each genuinely bucket by that real identity (one row per real session/component) rather than collapsing through a shared date bucket, matching the corrected model (§0-R4.1).
  - A coverage/role toggle (plain-language: "Show partial/incomplete readings too" / "Include values other systems calculated from other values") defaulting to the safe/inclusive-but-flagged default.
  - **Compare to (Round 3, new — KPI only, matching `supports_comparison_period`)** — *None / Previous period / Same period last year* — when set, the KPI additionally fetches and shows the shifted-period number and the delta (model report §0-R3.1 step 8); a small "vs. [date range]" caption under the KPI names exactly which real dates the comparison covers, never an unlabeled arrow.
  - **Source policy** — a segmented control: *All sources (flag conflicts) / Manual only / A specific import connection / API / CSV / Calculated* — **shown only for a Metrics-Core metric.** For a built-in series (RPE, sRPE, Duration) this ENTIRE control is hidden, not merely defaulted or disabled — those facts have no source-policy concept at all (model report §0-R3.7: built-in series use `source_policy='not_applicable'` under the hood, a value that is never user-facing and never offered as a choice). Picking "A specific import connection" opens the same connection picker already used elsewhere, scoped to connections visible to this dashboard's own data workspace (model report §0-R3.6).
  → drops onto the grid at the first free position, sized at that type's own `default_width`/`default_height`.
- **Drag** — a widget's whole header area is the drag handle; dragging shows a live "ghost" outline at 12-column granularity; drop is rejected (widget snaps back, brief shake) if it would overlap another widget — matching the DB's own deterministic-reject behavior (model report §0.5), never a silent auto-push of other widgets. A drag-drop swap (dropping widget A directly onto widget B's own slot) is offered as an explicit "Swap positions?" confirmation rather than a rejected overlap, since the model now supports a genuine atomic swap (model report §0.5) — accepting it stages both widgets' new positions for the next Save.
- **Resize** — a small handle at the widget's bottom-right corner, constrained live to that widget type's own min/max size (model report §0.6/`dashboard_widget_types`) — the handle simply cannot be dragged past the bound, no error message needed. If the widget's own type was since deactivated by an admin (model report §0.6), it can still be resized within its OLD bounds (deactivation blocks only NEW widgets of that type, never editing an existing one).
- **Per-widget menu** (small `⋮` in each widget's own header, Edit mode only) — Edit series/metrics (same options panel as Add widget, including switching widget TYPE — Round 2: if switching type would now violate the existing series' own cap or axis-unit compatibility, model report §0.6, the picker disables that target type with a one-line reason: *"This widget has 2 series — a KPI only supports 1"*), Change type-specific display options, Collapse (`state='collapsed'`, model report), Remove.
- **Save / Discard — an ATOMIC batch operation (Round 2, model report §0.5).** A small bar appears at the bottom once anything has changed (position, size, added/removed widget, series edit): "Discard changes" / "Save layout". Discard reverts every touched widget to its last-loaded position/size in the browser (nothing was ever sent). Save sends the WHOLE set of position/size/mobile-order changes in one call (`replace_dashboard_layout` for 2+ widgets moved together, or `update_widget_layout` when only ONE widget's position/size changed — model report §0-R3.4; the frontend never issues a raw position/size PATCH outside these two calls, since only they are proven deadlock-safe against each other) — either every change lands together, or none do; a swap or multi-widget rearrange can never partially apply. A stale-revision conflict (SQLSTATE `40001`/HTTP `409` — another editor saved first) surfaces as: *"This dashboard's layout changed while you were editing. Your changes were not saved — reload to see the latest version."* — never a silent overwrite, matching model report §0.3/§0.5. **Round 3 correction:** a position/size change now visibly updates the dashboard's own "last edited" state too (not just the one widget) — any other open viewer's dashboard-level cache is invalidated by a layout move, not only by adding/removing a widget, matching the corrected revision contract (model report §0-R3.4). Series/content edits (not position/size) still save individually as they're made, each against its own widget's own revision, exactly as in Round 1/2.

## Tablet (~600–959px)

- The SAME 12-column grid model, rendered at reduced effective density: widgets are laid out using their own stored `x`/`width` but visually scaled/wrapped so nothing requires horizontal scroll of the *page* — this is a **responsive reduction of the desktop grid**, not a second stored layout (model report §0.5/§D3). In practice: columns 7-12 wrap to a second visual row beneath columns 1-6 for any widget whose `x+width` would otherwise exceed the tablet's own reduced column count, preserving relative left-to-right/top-to-bottom order.
- Drag/resize stays available (tablet has room for direct manipulation) but touch-sized (larger handles, same overlap-reject/atomic-swap behavior as desktop).
- Global filter control collapses labels but keeps the same three-part shape (period/activity/athletes); the private-dashboard "Data: Club A" label collapses to a small badge next to the dashboard name.

## Mobile (< 600px)

- **Single column**, ordered by each widget's own `mobile_order` — never `x`/`y`/`width`/`height` (those are meaningless below the grid breakpoint).
- **No free drag/resize.** In Edit mode, each widget instead gets **Move up / Move down** controls (matching the "no free-form drag on mobile" rule already established for the Calendar's own month view and every other mobile-constrained control in this app). **Round 2 correction:** every Move up/down tap during one Edit session stages a pending `mobile_order` change locally (shown immediately, optimistically) — nothing is sent to the server until the SAME "Save layout" action used on desktop, which submits the WHOLE batch of mobile-order changes through the SAME atomic `replace_dashboard_layout` call (model report §0.5). A sequence of taps can never be left half-applied by a dropped connection partway through, and "Discard" simply drops the staged local changes with zero server calls.
- **Table widgets** get their own internal horizontal scroll container (`overflow-x: auto` on the table wrapper only — exact same pattern as the Calendar Results table) — the page itself never scrolls horizontally, verified the same way the Calendar phase verified it (`document.documentElement.scrollWidth <= clientWidth` at 360/375/390px, zero overflow).
- **Calendar/activity context stays visible** — when opened from an activity, a slim, non-scrolling context bar ("9 Sep 2026 › Morning Strength") stays pinned above the widget list, exactly mirroring the Calendar's own context bar component (not a new pattern) — tapping it returns to the Calendar view without losing the dashboard's own scroll position on return (same `view-cache.js`-backed instant-redisplay behavior as switching Calendar tabs). Same Round 2 rule as desktop: this is always a runtime filter, never auto-saved.
- **Add widget** on mobile opens the same type→series picker as desktop (including the Round 3 combine/group-by/comparison/coverage/source controls, in the same order but full-screen), and appends the new widget to the *bottom* of the mobile order (never asks for a manual mobile-position pick on creation — that's what Move up/down is for afterward).
- KPI widgets stack as compact single-row tiles (icon + value + label), never full-width empty space around a single number.
- **Unit conflict / measurement conflict / access revoked** — the same neutral, non-color-only states as desktop (above), stacked full-width.

## Template cloning and the ambiguous-metric state (Round 2, new)

- Cloning a system/club/team template opens a lightweight, full-panel review step (not a silent background operation) BEFORE the new dashboard is created: each of the template's widgets is shown with its resolved (or unresolved) series.
- A series whose hint resolved to exactly one visible candidate shows normally, with a small "from template" tag, editable like any other series afterward.
- A series whose hint resolved to **zero** visible candidates (model report §0.8, "safe degradation") shows a neutral "Not available in this workspace" placeholder and is simply omitted from the created dashboard unless the coach explicitly picks a replacement right there.
- A series whose hint resolved to **two or more equally-valid candidates** (`needs_resolution`, model report §0.8) is never auto-picked — it shows an inline picker pre-scoped to just those candidates: *"This template's 'Load' metric could mean either of these — pick one:"* with the small set of real options, defaulting to nothing selected (the coach must choose, or leave it omitted).
- Only after this review does "Create dashboard" become active — the clone itself is then a single atomic operation (new dashboard + resolved widgets + resolved series, or nothing, matching the model's own transactional guarantee).

## Accessibility (all breakpoints)

- Every widget is a labelled region (`aria-label` = widget title); the grid container has `role="list"`, each widget `role="listitem"`.
- Drag handles are also operable via keyboard in Edit mode (arrow keys move by one grid unit on desktop/tablet; on mobile the Move up/down buttons are the only mechanism, already keyboard-native).
- The global filter control and per-widget menus follow the exact same `aria-expanded`/focus-return conventions already used by the Calendar's own filter picker and metric picker — not reinvented.
- Focus never disappears after a re-render (same rule already enforced for Calendar/Results — carried forward here as a hard requirement, not a nice-to-have).
- Color is never the *only* signal: a conflict cell, a unit-conflict notice, an access-revoked panel, an error widget, and a collapsed widget each also carry a distinct icon/label, not just a color change.
